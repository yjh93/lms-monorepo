# ADR 0001. 어드민은 SPA(Vite), 학습자 사이트는 Next.js로 나눈다

- 상태: 채택
- 날짜: 2026-10-16

## 맥락

같은 도메인(강좌·수강생·수업)을 다루지만 사용자와 요구가 다른 두 화면이 있다.

|        | 운영 어드민                          | 학습자 사이트                            |
| ------ | ------------------------------------ | ---------------------------------------- |
| 사용자 | 로그인한 운영자·강사                 | 비로그인 방문자(기업 담당자)             |
| 핵심   | 필터·정렬·폼·대량 데이터 등 상호작용 | 검색 노출, 첫 화면 속도, 공유 미리보기   |
| SEO    | 불필요(`noindex`)                    | 필수                                     |
| 데이터 | 사용자별·권한별, 자주 바뀜           | 대부분 공개·공통, 일부만 자주 바뀜(좌석) |

## 결정

- **어드민: Vite + React Router SPA.** 정적 파일로 배포하고, 서버 상태는 TanStack Query로 관리한다.
- **학습자 사이트: Next.js 16 App Router.** Server Components로 HTML을 서버에서 만들고, Cache Components로 정적 셸과 스트리밍을 섞는다.

## 근거

- 어드민은 로그인 뒤에만 쓰이고 검색 노출이 필요 없다. 화면 대부분이 상호작용이라 서버 렌더링 이득이 작고, SPA가 배포·인프라(정적 호스팅)와 개발 루프(Vite HMR)가 단순하다.
- 학습자 사이트는 첫 HTML에 콘텐츠·메타데이터가 있어야 검색과 공유 미리보기가 된다. 강좌 정보처럼 모두에게 같은 데이터는 캐시된 정적 셸로, 좌석처럼 자주 바뀌는 데이터만 요청 시점에 스트리밍하는 구성이 App Router에 잘 맞는다.
- 수강 신청은 Server Action으로 처리해 JS가 로드되기 전에도 폼이 제출되고(점진적 향상), 검증 로직이 서버에 남는다.

## 결과

- 두 앱이 같은 공용 패키지(`@lms/api-client`, `@lms/ui`, `@lms/utils`)를 쓰도록 패키지 경계를 설계해야 한다 → [ADR 0002](0002-monorepo-package-boundaries.md)
- `@lms/ui` 컴포넌트는 서버 컴포넌트에서도 import될 수 있어, 훅을 쓰는 컴포넌트에만 `'use client'`를 붙인다.
- 어드민 번들은 초기에 한 덩어리였다. 무거운 화면(출석 분석)부터 라우트 단위 지연 로딩을 적용했다.

## 검토한 대안

- **둘 다 Next.js**: 어드민도 서버 컴포넌트로 만들 수 있지만, 권한별 데이터·빈번한 상호작용 위주라 서버 렌더링의 이점보다 서버 운영 비용과 캐시 설계 복잡도가 크다.
- **둘 다 SPA**: 학습자 사이트의 SEO·OG를 위해 별도 프리렌더링 도구가 필요하고, 폼 제출이 JS에 전적으로 의존한다.
